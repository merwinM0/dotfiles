# 编码前的文档检查

每次开始编写或修改代码前，必须先执行以下步骤：

1. 检查当前项目根目录是否存在 `README.md`、`README.en.md`、`AGENTS.md` 和 `READMAP.md`；如果已有 `ROADMAP.md`，则沿用该文件作为路线图，不重复创建 `READMAP.md`。
2. 对已存在的文件及相关 `docs/` 文档，先阅读并遵循其中的项目说明、开发约定和路线规划，不得直接覆盖。
3. 如果缺少必需文档，先查看项目目录结构、现有代码、配置及测试，了解项目的实际情况，再按照下述规则创建缺失文件并填写有依据的内容，不得只创建空文件或凭空编造。
4. 完成上述检查和必要的文档补充后，再开始本次编码工作。

# 文档组织与维护

项目文档按以下结构组织，其中 `docs/` 及其文件均按实际需求创建，不要求全部具备：

```text
README.md             # 中文版，默认展示
README.en.md          # 英文版，与中文版同步维护
READMAP.md            # 项目路线图；已有 ROADMAP.md 时沿用
AGENTS.md             # 编码与协作约定
docs/
├── ARCHITECTURE.md    # 架构设计
├── FEATURES.md        # 功能说明
├── API.md             # 接口文档
├── DEPLOYMENT.md      # 部署与运维
├── UI.md              # 界面与交互设计
└── CHANGELOG.md       # 版本变更记录
```

- `README.md` 主要用于介绍项目：项目是什么、解决什么问题、面向哪些用户，以及核心特点。保持简洁，可保留必要的快速开始，并链接到相关详细文档，避免堆放架构、接口、部署等长篇说明。
- `README.md` 使用中文，作为默认入口；同时创建英文版 `README.en.md`，两份文件顶部提供语言切换链接。新增、修改或删除 README 内容时，必须同步更新中英文两版，确保信息、示例、命令和链接一致。
- `READMAP.md`（或已有的 `ROADMAP.md`）记录已实现的功能、明确的待办事项和后续计划；无法从代码或现有资料确认的计划，应标注为待确认。
- `AGENTS.md` 说明目录结构、编码约定、开发流程和验证命令。指令文件统一使用这一名称，不再另建不同大小写、单复数变体或兼容链接。
- 只有项目确有对应内容或文档需求时，才创建 `docs/` 下相应文件；不为凑齐目录结构创建空文件或无实际内容的占位文档。已有相关文档时优先补充，避免重复。
- 修改代码涉及已有文档描述的行为、配置、接口或流程时，同步更新相关文档；涉及 README 时，始终同步维护中英文两版。

# 修改后的 Git 提交

1. 每次完成修改后，检查本次修改涉及的文件是否位于已有的 Git 仓库中；如果涉及，则在相应仓库中提交本次修改，提交说明必须使用中文，准确概括变更内容。
2. 只暂存和提交本次任务产生的修改，不得夹带用户其他未提交的改动；无实际变更时，不创建空提交。
3. 如果本次修改未涉及任何已有 Git 仓库中的文件，则无需提交。
4. 禁止自行运行 `git init` 或以其他方式创建 Git 仓库；Git 仓库由用户自行创建。

# 多步骤工作的任务进度上报

- 对需要多个执行、修改或验证步骤的工作，使用 `pi-task` 报告进度；简单问答不必建清单。先用 `command -v pi-task` 确认命令可用，不可用时说明情况，不擅自安装、不阻塞正常工作。
- 允许先进行少量只读检查，再在主要工作开始前确定清单。按可验收阶段拆分，不把每次工具调用都当成一个步骤。同一项工作只建立一份清单，相关追问继续更新；独立工作另建清单。
- 一次提交标题和全部初始步骤：`pi-task start --title "工作标题" --task "第一步" --task "第二步"`。步骤较多时可用 `--file -` 从标准输入提交 JSON 字符串数组。不要在标题、步骤或备注中保存密钥、密码等敏感信息。
- 记住 start 返回的工作 ID，后续每次写入显式传入 `--id ID`。不同 Bash 工具调用不保证共享变量，禁止通过“最近一次工作”推断写入目标，避免多个 Pi 会话串线。
- 开始一步时执行 `pi-task update --id ID --task 1 --state running`。只有实际完成并满足验证要求后才标记 done；测试步骤以真实测试结果为依据，必要时用 `--note "验证依据"` 附简短说明。工具返回或模型结束回答不等于任务完成。
- 优先合并相邻状态变化，减少工具开销：`pi-task update --id ID --task 1 --state done --next 2`。只提交变化，不重复发送完整清单，不为刷新或耗时而轮询 status。
- 发现新步骤时用 `pi-task add --id ID --text "新步骤"` 增补；修订标题用 update 的 `--text`，阻塞用 `--state blocked --note "原因"`。不得覆盖已有进度或隐藏未完成事项。
- 包括验证和 Git 提交在内的所有步骤都完成后，执行 `pi-task finish --id ID`。失败或取消时，能报告则用 `finish --id ID --state failed` 或 `finish --id ID --state cancelled` 结束；不得把未完成步骤自动打勾，也不保证异常中断时一定能够上报。
- 上报失败必须如实说明，修正参数或重试，不假装面板已更新。若与真实工作命令合并执行，必须保留工作命令的退出码，不能用无条件的后续命令宣布成功。监看器本身不执行任务，也不独立证明结果正确。
- 用户在另一个终端直接运行 `pi-task`，即可选择最近 5 次工作并实时查看。代理不要在工具里启动交互查看器；确需核对记录时使用带 ID 的 `status --once` 或 `status --json`。用户使用 fish，手动保存 ID 应使用 `set -l run_id (...)`，不要给出仅 Bash 支持的变量赋值或 heredoc 用法。
