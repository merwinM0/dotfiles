# CLI 输出设计

**适用范围：** 使用直接输出的 24 位 ANSI True Color、常见颜色的柔和淡色系和圆角终端面板设计 CLI 输出。重要结果与操作放在框内，常规进度放在框外。适用于新建或修改终端报告模块、状态摘要、错误展示和共享输出规范。通过语言无关的自然语言与图例，指导 Bun TypeScript、Go、Rust、C、uv 管理的 Python、Java 及其他语言实现，涵盖 Unicode 显示宽度、安全换行和纯文本回退。

**技能名称：** `design-cli-output`。**许可：** MIT。

构建平静、清晰、层级一致的终端输出：直接使用 ANSI 配色，用圆角面板承载重要信息，其他内容使用普通文本行。不同语言实现遵循同一份设计约定。

## 何时使用

- 新建或修改 CLI 报告模块或共享终端格式化层。
- 展示执行结果、重要配置、错误或用户必须采取的下一步操作。
- 让多个命令或不同语言实现保持一致的视觉语言。
- 修复换行、对齐、终端兼容性或过度装饰问题。

## 核心规则

- 所有自定义终端颜色直接使用 24 位 ANSI True Color 输出，不使用颜色／样式封装库，也不另建依赖某个库的配色体系。
- 优先使用常见绿色、红色、黄色、蓝色、青色、紫色和灰色的柔和淡色版本。避免荧光色、渐变、彩虹文字和大面积填充背景。
- 用圆角线框面板承载值得关注的信息，不给每一行文字或每次进度更新都套框。
- 保留终端自身的背景和默认正文颜色。颜色用于点缀，不能成为理解信息的前提。
- 格式化与业务逻辑、实现语言分离。优先遵循本规范的自然语言约定和图例，不机械复制某种语言的函数。
- 不为实现这套视觉风格而额外发明输出模式或命令行标志；保留项目已有的命令和数据约定。

## 配色与直接 ANSI 输出

### 语义化配色

所有命令共享一套语义化配色。以下颜色是自定义的起始参考，不是强制终端主题。淡色值适合深色终端背景；浅色背景使用同一常见色相的较深版本，以保证可读性。

| 语义角色 | 常见颜色 | 淡色 HEX | RGB | 浅色背景使用的较深版本 |
| --- | --- | --- | --- | --- |
| `success` | 淡绿 | `#A7D8A8` | `167, 216, 168` | `#27633B` |
| `error` | 淡红 | `#F2A6A6` | `242, 166, 166` | `#A12E36` |
| `warning` | 淡黄 | `#E8D58B` | `232, 213, 139` | `#796000` |
| `info` | 淡蓝 | `#9FC5F0` | `159, 197, 240` | `#285F9A` |
| `accent` | 淡青 | `#9ED9D7` | `158, 217, 215` | `#246C6A` |
| `highlight` | 淡紫 | `#C6B4E7` | `198, 180, 231` | `#6B469B` |
| `muted` | 淡灰 | `#ABB3BF` | `171, 179, 191` | `#526071` |
| `border` | 中性灰 | `#8D99A8` | `141, 153, 168` | `#657284` |

状态标签使用 `success`、`error` 和 `warning`；标识符及有用的上下文使用 `info`；主标题使用 `accent`；选中值可少量使用 `highlight`。边框通常保持中性。次要文字可以弱化，但必须清晰可读；普通段落使用终端默认前景色。

不要为了让淡色文字可读而强制设置深色背景。已知是浅色背景时使用较深版本；背景未知时，重要文字保持终端默认前景色，克制使用点缀色，不要猜测浅色文字一定可读。

以 `#18181B` 和 `#FFFFFF` 为参考背景时，上述对应配色计算所得的 sRGB 对比度均不低于 4.5:1。这不代表适用于任意终端主题：仍需核对实际前景／背景组合，必要时调整或取消某个点缀色。不要只靠颜色表达状态，应同时使用 `OK`、`WARN`、`ERROR` 等文字。

### ANSI 输出约定

- `ESC` 表示实际的转义字符 U+001B，而不是三个可打印字母。前景色使用 `ESC[38;2;R;G;Bm`，RGB 各通道为 0–255 的整数。
- 仅在确有必要时使用背景色序列 `ESC[48;2;R;G;Bm`。普通输出和面板内部均继承终端背景。
- 每个带样式片段结束时使用 `ESC[0m` 复位，不让颜色或强调样式泄漏到填充空格、后续行或用户的 shell 提示符。
- 先对清理后的纯文本计算宽度、换行和填充，再应用可信样式。ANSI 序列不占显示列，换行时也不能将其拆开。
- 所有人类可读输出路径，包括错误和进度，都遵循同一套语义配色与 ANSI 规则；不要为另一个命令或语言引入不同的渲染依赖。

### 能力检测与纯文本回退

针对实际的目标输出流检测能力，而不是只判断整个进程。stderr 连着终端，并不意味着已重定向的 stdout 仍是交互式输出。

在支持 True Color，或用户明确要求启用时使用 True Color。`COLORTERM=truecolor`、`COLORTERM=24bit` 可以作为判断依据之一，但仅有 TTY 并不能证明支持 24 位颜色。遵循项目已有的能力检测和用户覆盖机制，不额外发明标志。

当 `NO_COLOR` 非空、`TERM=dumb`、输出目标不是终端，或颜色能力不支持／不确定时，默认回退为纯文本；不要悄悄替换成 16 色或 256 色配色。关闭颜色后不输出任何样式转义序列，包括复位和粗体。即使用户明确要求颜色，也不能装饰机器可读输出。

颜色能力与 Unicode 能力分开判断。支持 Unicode 的终端在关闭颜色后仍可保留圆角边框；无法渲染线框字符时，使用 ASCII 边框或无框文本。管道和文件通常应接收稳定、无颜色的普通文本行，而非装饰性面板；机器可读输出绝不能包含面板或 ANSI 样式。

## 圆角面板

### 框内与框外的信息分配

框内放置用户必须注意的信息：
- 本次操作的最终结果或简洁状态摘要。
- 重要目标、选定配置和主要输出位置。
- 失败原因及下一步修复操作。
- 命令本来就需要的确认信息或破坏性操作警告。

框外保留轻量的常规信息：
- 进度更新、普通逐项日志和后台活动。
- 详细诊断、耗时、日志文件位置和次要提示。
- 不影响主要结果或必要操作的补充上下文。

一次操作优先使用一个主要面板。确有相互独立的结果时才使用额外面板，避免嵌套和反复套框。不要在框内、框外重复同一份摘要，也不要把重要错误埋在外围日志中。

### 布局约定

采用 `terminalPanel` 风格的渲染器，并遵循以下与语言无关的约定。渲染器接收标题、由文本行或分隔标记组成的只读序列，以及可选列宽预算，返回完整字符串；何时输出、输出到哪里，由调用方决定。

1. 圆角使用 `╭`、`╮`、`╰`、`╯`，横线使用 `─`，侧边使用 `│`，内部分隔线两端使用 `├` / `┤`。边框采用单显示列的线框字符，不使用 emoji。
2. 规范化列宽预算：缺失、非有限数或非正数时使用 80，否则向下取整，再限制到 6–88 列。已知目标终端实际宽度时，即使传入的预算更大，也不能超过实际宽度；已知终端不足 6 列时，改用无框文本，不强行输出溢出的面板。
3. 首选面板宽度取以下值中的最大值：40 列、标题显示宽度加 5、每个内容行显示宽度加 4。实际宽度取首选宽度与可用预算中的较小值。40 只是偏好，不是窄终端上的硬性最小值。
4. 每个内容行依次为左边框、一个空格、内容、补齐用空格、一个空格、右边框。内部内容宽度等于面板宽度减 4；所有面板行的显示宽度必须一致。
5. 标题显示宽度不超过面板宽度减 5 时，将标题嵌入顶边，如下方图例所示。放不下时，使用普通顶边，将标题按内部内容宽度换行放入框内，再添加分隔线。空标题只使用普通顶边，不额外生成无意义的标题行。
6. 分隔标记（在使用该表示方式的语言中为 `null`）生成一条完整的内部分隔线。空字符串生成一行带填充的空白内容，不等同于分隔线。
7. 先按内容中的显式换行拆行，再将每行折行至内部宽度；保留有意设置的空白行。条件允许时优先在单词边界换行，但长路径、URL 和连续长单词应在安全字素边界拆分，不得溢出或静默截断。
8. 使用圆角底边结束，并以换行符连接各行。最终输出换行留给调用方，便于与框外消息组合，避免重复空行。

## 文本安全、显示宽度与换行

- 标题、路径、服务端响应等传入值都是文本，不是终端指令。布局前移除内嵌 ANSI/OSC 序列和不安全控制字符，不让不可信内容移动光标、修改终端标题或注入样式。合法换行和制表符按下述规则规范化处理。
- 将 CRLF 和 CR 行尾统一为换行符；标题中的换行替换为空格，内容中的换行保留为行分隔。测量和折行前，将制表符替换为四个空格。
- 测量终端显示列，而不是字节数、UTF-16 单元数或 Unicode 码点数量。汉字、组合字符、emoji 和零宽连接符序列的宽度不能混为一谈。
- 按字素簇分割文本，使用能够正确处理目标文本的终端宽度实现。不得为了填满一行而拆开 UTF-8 序列、代理对、组合序列或 emoji 字素簇；连一个完整字素簇都无法安全放入时，回退为无框文本。
- 测量、折行和渲染必须使用同一套宽度规则。在实际终端检查中英文混排和 emoji；字体、终端行为可能与库的假设不同。
- 面板渲染器不依赖全局可变状态，也不产生直接打印副作用。共享文本清理、显示宽度、换行、能力检测和 ANSI 样式等小型辅助功能，不在每个命令中重复实现。

## 不同语言的适配

布局与配色才是规范，不限定具体源语言。将约定适配到已选技术栈，不为此引入另一种运行时或高级样式框架。

| 语言／运行时 | 适配要点 |
| --- | --- |
| Bun TypeScript | 使用 `Bun.stringWidth` 测量终端列宽，配合 `Intl.Segmenter` 等字素感知的分割方式。JavaScript 字符串长度不等于显示宽度。 |
| Go | 字符串和字节长度不是终端列数。使用合适的 Unicode 显示宽度实现与字素分割，ANSI 输出与布局分离。 |
| Rust | 字节长度和字符数量都不等于显示宽度。使用 Unicode 显示宽度与字素分割支持，折行和填充共用一套规则。 |
| C | 正确处理 UTF-8 和 locale。`wcwidth` / `wcswidth` 可辅助列宽测量，但不能单独解决所有 emoji 或字素问题；安全处理非法输入和缓冲区边界。 |
| uv 管理的 Python | uv 管理环境，不负责渲染。使用显示宽度和字素感知工具，不使用 Python 字符串长度代替列宽；直接输出同样的 ANSI 序列。 |
| Java | `String.length()` 统计 UTF-16 单元，码点数量也仍不等于显示列数；使用合适的显示宽度与字素处理方式。 |
| 其他语言 | 利用对应运行时的合适能力，保持相同的配色、文本清理、宽度计算、面板几何和回退行为。 |

为正确处理 Unicode 而使用显示宽度或字素分割依赖是允许的；这里限制的是用颜色／渲染封装库取代直接 ANSI 样式。在 Windows 上，还需检查虚拟终端支持和 Unicode 输出能力，宿主不支持时使用纯文本回退。

## 文案与输出通道

- 使用简洁、客观的语言，说明发生了什么、影响什么，以及用户下一步应做什么。
- 各命令术语保持一致，不用隐喻、仪式化叙事或安慰性但失真的摘要替代真实错误。
- 优先使用简单状态文字，不依赖 emoji 和动画装饰。报告实际结果，不将部分完成标记为成功。
- 保留项目已有的 stdout/stderr 和退出码约定。stdout 承载机器数据时，将进度和诊断放到合适的独立输出流，数据本身不添加装饰。
- 框内和框外日志都不得泄漏密钥或敏感值。面板醒目不构成展示更多数据的理由。
