# CLI Output Design

Keep output calm and readable: a named rounded overview for groups of useful information, with brief status lines and details outside. For implementation or validation, read [Implementation reference](references/implementation.md) for the palette, ANSI sequences, runtime guidance, and test matrix.

## 1. Preserve the output contract

- Identify the destination and audience of each output path. Preserve the project's stdout/stderr assignments, exit codes, established output modes, and parsable formats. Machine-readable output never receives panels, markers, or style escapes, even when human output is explicitly styled.
- Use the existing override mechanism; do not add flags or modes just for this design. Do not invent metadata, checks, or API results to fill a panel.
- Say what happened, what it affects, and what to do next when applicable. Keep sensitive values out of reports and logs. Do not imply success for partial or failed work.

## 2. Choose presentation for each human-facing stream

Check the actual destination of that stream. An interactive stderr does not make redirected stdout interactive. Treat framing, color, and Unicode as separate choices and honor the project's documented human-output behavior. Where the project does not define behavior, use these defaults:

| Choice | Default behavior |
| --- | --- |
| Framing | Use a panel for a useful interactive overview or grouped result. Use unboxed text for standalone errors, progress, and per-item logs, and plain lines without decorative markers for files, pipes, and `TERM=dumb`. |
| Color | Never style a terminal host known not to handle the required escapes. Otherwise, an explicit existing user color setting wins over automatic detection. In automatic mode, disable styles (including resets and bold) for non-empty `NO_COLOR`, `TERM=dumb`, a non-terminal stream, or unconfirmed True Color support. A TTY alone is not proof; `COLORTERM=truecolor` and `COLORTERM=24bit` are hints. |
| Unicode decoration | Use box-drawing glyphs and outside markers only if renderable and each chosen glyph occupies one column under the destination's width policy. Use ASCII where a glyph set is unsupported or its one-column width under that policy cannot be verified. This choice does not transliterate the content. |

`NO_COLOR` alone does not remove a panel or its Unicode glyphs. For human-readable redirected output, explicitly forced color can style plain lines without enabling a panel. Use direct 24-bit ANSI for custom colors, not a styling wrapper or a 16/256-color substitute. Use a shared soft semantic palette, inherit the terminal background and default body foreground, and state every status in words. Avoid neon, gradients, and large filled backgrounds.

## 3. Prepare text before layout

- Treat supplied titles, URLs, paths, and responses as text. Strip embedded terminal escape/control sequences, including incomplete sequences, and remove unsafe controls. Preserve line breaks and tabs only for the field normalization below. Do this even when color is off.
- Normalize CRLF and bare CR to LF. Replace line breaks with spaces in single-line fields such as titles, links, metadata, and status values. Preserve breaks only in designated multiline details; continuation indentation is generated by the renderer. Replace tabs with four spaces before measuring.
- Measure terminal columns, not bytes, UTF-16 units, or code points. Use grapheme-aware segmentation and one width policy for measuring, wrapping, and padding. Prefer word breaks; split long unbroken text at grapheme boundaries without truncation. If a complete grapheme cannot fit, leave the panel off rather than splitting it.
- Keep the renderer pure: pass in prepared content, widths, and presentation settings; return text without printing. Apply trusted ANSI styling only after layout.

## 4. Lay out the overview and surrounding text

- Use one panel for the main outcome; additional panels are for genuinely separate outcomes. Put the name near the left of the top border. Put the literal primary URL or location first in the body, at full inner width; omit it if absent. Keep it on one physical line when it fits and wrap it without truncation when it does not. Put overview metadata or the final result below, using blank space rather than automatic dividers. Keep routine status, database state, and API details outside. A grouped critical failure may put its cause and corrective action inside the panel.
- Default the width budget to 80 if missing, non-finite, or non-positive; otherwise round down and clamp to 6–88. Cap it at the known destination width. If that width is below 6, use unboxed text.
- When both ordered metadata groups are non-empty and the budget is at least 56, use two columns and prefer a panel width of `min(budget, 72)`. Otherwise use one column and prefer `min(budget, 40)`. A long title or primary line may widen the panel within the budget. In single-column layout, retain all fields in first-group-then-second-group order.
- A body row is a side border, one space, content padded to `panel width − 4`, one space, then a side border. In two-column layout, reserve a four-column gap, split the remaining inner width equally (odd extra column on the right), and wrap paired fields separately. Pad the shorter cell on continuation rows and leave a missing partner blank. Keep every frame row the same display width.
- Use `╭`, `╮`, `╰`, `╯`, `─`, and `│` for the frame. If a non-empty title fits in `panel width − 5`, use `╭─ <title> `, then enough `─` to fill before `╮`. Otherwise use an untitled top edge and wrap the title into body rows followed by a blank row. An empty title needs no extra row. Empty content rows are padded; only an explicit divider uses `├` and `┤`. Return joined rows without a trailing newline. Leave one blank line before any outside status area.
- Use `○` for state and `◇` for detail headings, always with labels. `○` is not a success symbol. Indent details and wrapped continuations to align after the marker and space. If Unicode decoration is unavailable, use `+`, `-`, `|` for an ASCII frame and `-` for either marker. Omit markers and indentation when the prefix and first label grapheme cannot fit. Add no other decorative symbols, icons, emoji, or animations; this does not limit literal input text.

The same content at 72 and 40 columns. The wide layout uses two 32-column cells with a four-column gap. The narrow layout keeps every field in group order. These are composition examples, not required fields.

## 5. Verify the result

Check a styled interactive stream, an unstyled interactive stream, and redirected or machine-readable output independently. Check the 55/56-column boundary, mixed-width content, and safe handling of supplied controls and line breaks. Run the [reference checks](references/implementation.md#validation) in the target stack; a matching diagram alone does not establish terminal compatibility.
